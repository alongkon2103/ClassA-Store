ช่วยเพิ่ม API สำหรับเชื่อมสิทธิ์ซื้อเกมจากเว็บร้านค้านี้เข้ากับโปรแกรม Tikkies

ให้ตรวจโครงสร้างโปรเจกต์ ระบบล็อกอิน Google/Discord ฐานข้อมูล รายการซื้อ การคืนเงิน และระบบสิทธิ์เดิมก่อน จากนั้นใช้รูปแบบและเครื่องมือที่โปรเจกต์ใช้อยู่ ลงมือทำพร้อมทดสอบให้ครบ โดยรักษาข้อมูลลูกค้าและระบบซื้อขายเดิม

## เป้าหมาย

Tikkies จะมีแท็บ Games แสดงเกม Roblox ที่ร้านจำหน่าย ผู้ใช้ล็อกอิน Tikkies แล้วระบบต้องตรวจได้ว่า:

- เป็นลูกค้าคนไหนของร้าน
- ซื้อเกมใดไว้ และสิทธิ์ยังใช้งานได้หรือไม่
- สิทธิ์นั้นผูกกับ Roblox บัญชีใด
- สิทธิ์หมดอายุ ถูกระงับ หรือถูกคืนเงินแล้วหรือไม่

Tikkies ต้องนำบัญชี Roblox ที่ใช้ซื้อมาแสดงอัตโนมัติ ผู้ใช้เลือกได้เฉพาะบัญชีที่มีสิทธิ์ของเกมนั้น

งานนี้ทำเฉพาะฝั่งเว็บร้านค้าและ API ไม่ต้องแก้โปรแกรม Tikkies หรือระบบรับอีเวนต์ใน Roblox

## 1. การจับคู่บัญชีลูกค้า

ใช้ตัวตน OAuth ที่ตรวจสอบแล้ว:

- Google: ใช้ `sub` หรือ provider account ID ที่ระบบเก็บจากการล็อกอิน
- Discord: ใช้ Discord user ID
- เก็บและเปรียบเทียบรหัสเหล่านี้เป็น string

ห้ามใช้อีเมล ชื่อแสดงผล หรือ username เป็นหลักฐานเพียงอย่างเดียวในการยกสิทธิ์ให้บัญชีอื่น

Tikkies backend จะส่ง provider และ provider account ID ที่ได้จากระบบล็อกอินของตัวเองมาให้ โดยข้อมูลเหล่านี้ต้องไม่รับตรงจากช่องกรอกของผู้ใช้

หากรับหลาย OAuth identities แล้วพบว่าชี้ไปคนละ customer ให้ตอบ `identity_conflict` และห้ามรวมบัญชีอัตโนมัติ

ถ้าลูกค้าซื้อด้วย Google แต่เข้า Tikkies ด้วย Discord และร้านยังไม่มีการเชื่อมสองบัญชีนี้ ให้รายงานว่าต้องเชื่อมบัญชีหรือใช้ผู้ให้บริการเดิมก่อน อย่าอ้างว่ารองรับโดยจับคู่อีเมลอย่างเดียว

## 2. API ตรวจสิทธิ์

สร้าง endpoint แบบ server-to-server:

`POST /api/integrations/tikkies/entitlements`

ตัวอย่าง request:

```json
{
  "identities": [
    {
      "provider": "google",
      "providerAccountId": "example-google-sub"
    }
  ]
}
```

อนุญาตเฉพาะ provider ที่รองรับจริง ตรวจชนิดข้อมูล ความยาว และจำนวน identities สูงสุดอย่างชัดเจน

ตัวอย่าง response:

```json
{
  "schemaVersion": 1,
  "customerId": "customer_123",
  "checkedAt": "2026-10-15T10:00:00Z",
  "entitlements": [
    {
      "entitlementId": "license_456",
      "gameKey": "zombie-arena",
      "gameName": "Zombie Arena",
      "universeId": "1234567890",
      "placeIds": ["9876543210"],
      "status": "active",
      "expiresAt": null,
      "updatedAt": "2026-10-15T09:00:00Z",
      "revision": 1,
      "roblox": {
        "userId": "1122334455",
        "username": "ExamplePlayer",
        "displayName": "Example Player"
      }
    }
  ]
}
```

รายละเอียด:

- `customerId` เป็นรหัสลูกค้าถาวรของร้าน
- `entitlementId` เป็นรหัสสิทธิ์ถาวร ไม่สร้างใหม่ทุกครั้งที่เรียก API
- `gameKey` เป็นรหัสเกมถาวร ใช้จับคู่กับรายการเกมใน Tikkies แม้เปลี่ยนชื่อสินค้า
- Roblox IDs และ OAuth IDs ส่งเป็น string
- แยก Universe ID กับ Place ID ให้ถูกต้อง ห้ามถือว่าใช้แทนกันได้
- `expiresAt: null` หมายถึงไม่มีกำหนดหมดอายุ
- วันเวลาทั้งหมดเป็น UTC ISO 8601
- `revision` เพิ่มขึ้นเมื่อข้อมูลที่มีผลต่อสิทธิ์เปลี่ยน เพื่อรองรับการซิงก์ในอนาคต
- ไม่ต้องส่งที่อยู่ เบอร์โทร รายละเอียดการชำระเงิน หรือข้อมูลส่วนตัวที่ไม่จำเป็น

สถานะที่ส่งออกให้กำหนดเป็นสัญญาที่ชัดเจน เช่น:

`active`, `pending`, `expired`, `revoked`, `refunded`, `account_unresolved`

มีเพียง `active` เท่านั้นที่ใช้ปลดล็อกเกมได้

ให้คำนวณจากแหล่งข้อมูลสิทธิ์และการชำระเงินจริงของระบบ ตรวจวันหมดอายุขณะอ่านด้วย ไม่พึ่งงานตามเวลาที่อาจยังไม่ได้รัน

กรณีตอบกลับ:

- พบลูกค้าแต่ไม่มีสิทธิ์: HTTP 200 และ `entitlements: []`
- ไม่พบบัญชีที่ตรงกัน: HTTP 404 พร้อม `customer_not_found`
- identities ขัดแย้งกัน: HTTP 409 พร้อม `identity_conflict`
- input ผิด: HTTP 400
- authentication ไม่ผ่าน: HTTP 401/403
- เกินโควตา: HTTP 429 พร้อม `Retry-After`
- ระบบสิทธิ์หรือฐานข้อมูลมีปัญหา: HTTP 503 ห้ามตอบว่าไม่มีสิทธิ์แทนข้อผิดพลาด

หากรูปแบบ route ของโปรเจกต์จำเป็นต้องต่างจากตัวอย่าง ให้รักษาความหมายของสัญญาและบันทึก path จริงในเอกสาร

## 3. ข้อมูล Roblox ที่ใช้ซื้อ

ตรวจว่าระบบเดิมเก็บ Roblox username หรือ User ID อย่างไร

- ใช้ Roblox User ID เป็นตัวผูกสิทธิ์หลัก
- username/display name ใช้แสดงผล และอัปเดตตามบัญชีเดิมได้เมื่อเปลี่ยนชื่อ
- หากมีแต่ username ให้ตรวจสอบผ่าน Roblox API ทางการ แล้วบันทึก User ID ที่ resolve ได้
- ห้ามเรียก Roblox API ใหม่ทุกครั้งที่ Tikkies ตรวจสิทธิ์
- สิทธิ์เก่าที่ resolve บัญชีไม่ได้ ให้คืนสถานะ `account_unresolved` พร้อมข้อมูลสำหรับแอดมินแก้ไข ห้ามเดาหรือปลดล็อกผิดคน
- การ resolve ชื่อเป็น User ID ไม่ถือว่าเป็นการพิสูจน์ความเป็นเจ้าของบัญชี Roblox

ถ้าลูกค้าซื้อหลายเกมหรือหลายบัญชี Roblox ให้คืนรายการสิทธิ์แยกกัน ห้ามเลือก Roblox username ล่าสุดของลูกค้าไปใช้กับทุกเกม

การเปลี่ยน Roblox ที่ผูกสิทธิ์ต้องผ่านกฎของร้านเดิมและมีบันทึกการเปลี่ยน ห้ามให้ API นี้เปลี่ยนบัญชีปลายทางได้เอง

## 4. Authentication และความปลอดภัย

API นี้ให้ backend ของ Tikkies เรียกเท่านั้น:

- ใช้ HTTPS และ credential สำหรับ integration โดยเฉพาะ
- ส่ง credential ผ่าน Authorization header
- เก็บค่าลับผ่าน environment/config ฝั่งเซิร์ฟเวอร์
- ไม่ใส่ใน frontend, URL, repository, response หรือ log
- มีวิธีเปลี่ยนและเพิกถอน credential
- จำกัดสิทธิ์ให้ integration นี้อ่านข้อมูลสิทธิ์ที่จำเป็นเท่านั้น
- จำกัด body size และ rate limit โดยคำนึงว่า Tikkies backend เรียกให้ลูกค้าหลายคน ไม่ตั้งโควตาต่ำจนตัดผู้ใช้ทั้งหมดที่ออกจาก IP เดียวกัน
- ตรวจ authentication ก่อน lookup ลูกค้า
- ตั้ง `Cache-Control: no-store` เพื่อไม่ให้ proxy/shared cache เก็บข้อมูลสิทธิ์
- บันทึก request ID, ผลลัพธ์ และเวลาตอบกลับ โดยไม่บันทึก token หรือ OAuth identities เต็ม ๆ

ห้ามให้ผู้ใช้เรียก endpoint นี้โดยกรอกอีเมลแล้วอ่านสิทธิ์ของคนอื่นได้

## 5. การซื้อ คืนเงิน และเปลี่ยนสิทธิ์

ข้อมูลที่ API คืนต้องสะท้อน:

- การซื้อที่ยืนยันสำเร็จจากระบบชำระเงิน
- การต่ออายุและหมดอายุ
- การคืนเงิน/เพิกถอน/ระงับ
- การเปลี่ยนบัญชี Roblox ตามกฎร้าน

ให้ตรวจ flow เดิมและอัปเดต revision/updatedAt ใน transaction ที่เหมาะสม ห้ามใช้สถานะชำระเงินที่ frontend ส่งมาเป็นหลักฐาน

รุ่นแรกใช้ API ตรวจสิทธิ์นี้เป็นแหล่งข้อมูลหลักได้ โดยเอกสารแนะนำให้ Tikkies ตรวจตอนเข้า Games/เริ่มเชื่อมเกม และ refresh สิทธิ์เป็นระยะ แนะนำแคชไม่เกิน 60 วินาที

ระบุชัดว่าการเพิกถอนอาจมีช่วงหน่วงตามรอบ refresh และห้ามแนะนำให้ Tikkies ใช้สิทธิ์จากแคชต่อไปไม่มีกำหนดเมื่อ API ล่ม

หากโปรเจกต์มีระบบ integration webhook/outbox อยู่แล้ว ให้เสนอการใช้ระบบเดิมส่งแจ้งสิทธิ์เปลี่ยนพร้อมลายเซ็น แยกเป็นส่วนเสริม อย่าเพิ่มระบบคิวหรือโครงสร้างพื้นฐานใหม่โดยไม่จำเป็นสำหรับ API รุ่นแรก

## 6. ฐานข้อมูลและประสิทธิภาพ

- ใช้ฐานข้อมูลและระบบสิทธิ์เดิม
- เพิ่ม index สำหรับ OAuth identity, customer, game และ entitlement ตาม query จริง
- หลีกเลี่ยง N+1 และการอ่านรายการซื้อทั้งหมดทั้งระบบเพื่อหาเจ้าของ
- ไม่สร้างระบบคำสั่งซื้อ/สมาชิกชุดใหม่ซ้ำกับของเดิม
- Migration ต้องรักษาข้อมูลลูกค้าเดิม ห้าม drop table หรือใช้คำสั่งยอมรับ data loss
- ถ้ามี backfill User ID ให้แยกเป็นงานที่รันซ้ำได้ มี dry-run และจำกัดอัตราการเรียก Roblox
- ไม่เรียกบริการภายนอกใน transaction ของฐานข้อมูลที่เปิดค้าง

ถ้าข้อมูลสินค้าเดิมยังไม่มี gameKey หรือ Roblox IDs ให้เพิ่ม mapping ที่แอดมินดูแลได้ตามรูปแบบโปรเจกต์ โดยไม่ต้องออกแบบหน้าร้านใหม่ทั้งหมด

## 7. การทดสอบที่ต้องมี

ทดสอบ route และกฎสิทธิ์จริงอย่างน้อย:

- Google/Discord identity ที่ตรงกัน
- อีเมลเหมือนกันแต่ provider identity ไม่ตรง ต้องไม่ยกสิทธิ์ให้
- identities หลายตัวชี้คนละ customer
- ไม่พบลูกค้า และพบลูกค้าแต่ไม่มีสิทธิ์
- ซื้อแล้ว, รอชำระ, หมดอายุ, คืนเงิน และถูกเพิกถอน
- หลายเกมและหลาย Roblox บัญชี ไม่คืนสิทธิ์ปะปน
- เปลี่ยน Roblox username แล้วยังผูก User ID เดิม
- สิทธิ์เก่าที่ resolve Roblox ไม่ได้
- ไม่ส่ง credential, credential ผิด และ rate limit
- ฐานข้อมูลล่มต้องตอบข้อผิดพลาด ไม่ตอบรายการว่าง
- ไม่มีข้อมูลลับหรือข้อมูลลูกค้าที่ไม่จำเป็นหลุดใน response/log
- ระบบล็อกอิน ซื้อขาย และคืนเงินเดิมยังทำงาน
